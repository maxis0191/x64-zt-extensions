## FF failure and restoration

The native lease was released before separate 8/11 GiB FF admission. The existing
stock binding was guarded and staged; baseline modes and the independent 77-byte
sentinel rule were preserved. The FF build Python root then exited one before
launching ZoneTool. Its requested log directory was `RunRoot/build`, already
occupied by native `writer.obj`, `two-bone-writer.exe` and `tmp`. The phase adapter
requires a fresh log directory and rejected this alias before Popen. The parent
then tried to read the absent `build/phase.json`, obscuring that initial error.

The cause was reproduced with the actual saved spec, substituting only the
restored-away staged executable path with its identical pinned source EXE and
mocking job/Popen calls. The mock raised `fresh phase log directory required`
without any Popen call. This is an orchestration failure, not an asset or geometry
rejection. Verify, dump and read-ff were never reached; no FF was produced.

All five original jobs were closed. The existing restoration helper confirmed
all 79 staged entries removed and source preservation before releasing FF
admission. Postchecks found unchanged source metadata and execution-input hashes,
no exact chain identities remaining, no rig lease, and Main's same process
identity and executable hash. SDK hash proof is the guarded runner's final proof;
the postcheck did not rehash the whole SDK or retail stock outside admission.
The original 27 files total 2,716,722 bytes including hidden files and the final
79,363-byte serialized state; both stored final/max counters equal that total.
